# Bonte agent workflows: setup and verification

Implemented against the bundled Casafari contract. This release has not been deployed and has not created live leads, calendar events or invitations.

## Enable the release

1. Back up the application database and apply `npm --prefix web run db:migrate` using the intended deployment database. The new `0002_wakeful_logan.sql` migration adds `workflow_records`; it does not replace chat/auth tables. The gateway refuses to start without this schema. The migration was tested on an isolated PostgreSQL engine, not applied to production during development.
2. Deploy the gateway and web together. Document **bytes** live in a private S3 bucket (`BONTE_S3_BUCKET` + `BONTE_S3_REGION` or `AWS_REGION`, default credential chain / IAM role). Local disk is not a runtime fallback or first-download path; missing S3 config is a setup error. Metadata, drafts and chat history stay in PostgreSQL. Preserve the `agent-output` volume for verified listing-link JSON, templates and scratch. Back up the database and old attachment tree, freeze writes, then inventory with `npm run attachments:migrate-s3` and copy with `--apply` only when `BONTE_S3_MIGRATE_CONFIRM` equals the destination bucket. The job copies complete live rows whose local bytes match stored hashes, keeps original expiry, and rolls back new S3 writes if metadata publish fails. Expired/invalid locators are left in place. Historical brochures copy only from oldest in-window assistant attachment proofs on `workspace_` chat ids; existing `generated_file` mappings are not resurrected. Rerun is safe. PutObject-then-crash can leave S3 orphans until bucket lifecycle; versioned buckets need version deletes to erase objects. This repository has not been used to deploy or cut over a production AWS bucket.
3. Use the updated gateway Docker image for Poppler, Tesseract (English/Portuguese), and LibreOffice Writer. For local development install those executables, or set their `BONTE_*_PATH` overrides from `.env.example`. DOCX extraction and template population use installed npm dependencies.
   On macOS, `brew install poppler tesseract tesseract-lang` supplies PDF extraction and OCR. Check `pdfinfo -v` and `tesseract --list-langs`; the configured `BONTE_OCR_LANGUAGES` must be installed (default `eng+por`). LibreOffice is only needed for DOCX-to-PDF rendering, not PDF/photo intake or the bundled NDA/CMI templates.
4. Ask the agent for workflow status while signed in. It reports this user's workspace/actor IDs and missing configuration. Ordinary CRM reads, local tasks, proposals and email drafts do not require enabling CRM writes or Calendar access. Property cards show the listing title (reference as fallback). Lead and property drawers fetch the latest record through authenticated `/api/crm`, not chat snapshots. Email drafts are not sent: Mail app opens `mailto:` with saved To/subject/body; blank To and ~30k-character bodies need manual paste, and attachments are downloaded by hand. Opening the mail app does not mark a draft sent. Native OS compose was not visually verified.

Uploads accept PDF, DOCX, JPEG, PNG and WebP, including passport photos, with a 15 MB file limit and 40-page PDF limit. Use the visible Documents control above the message box to select multiple files. Choose Party identification for client/agent IDs or passport photos, and Transaction for property/deal documents. Each upload belongs to its authenticated workspace and conversation. Successful uploads survive a failed file in the same batch; sending waits for processing, and documents can be sent without typed text. Sent document links remain in conversation history. The first 12 source documents in the list accompany each message; a notice explains the limit when more are retained.

Native PDF text is preferred; scans/photos use OCR with sparse-layout segmentation to retain identity fields. Runtime failures report missing PDF/OCR setup rather than inventing an empty one-page document or blaming the scan. After the runtime is repaired, evidence reads can recover previously failed uploads from their retained original bytes. This does not authenticate identity documents, and OCR-derived names, numbers and dates still need review.

Source documents and generated files default to 30-day retention (`BONTE_ATTACHMENT_RETENTION_DAYS`); users can delete them sooner. The background worker deletes the S3 object before dropping locator metadata so failed cleanups retry, and denies expired downloads even if cleanup fails. It runs inside the gateway every 30 seconds; there is no extra scheduler service. Follow-ups and monitor definitions persist until explicitly completed/cancelled. Due reminders and changed audit findings appear in Bonte, without sending email or broker messages.

The existing application uses a separate workspace for each signed-in user. Conversations, briefs, drafts, tasks and viewing records follow that boundary. This release does not introduce shared team chat history.

## CRM semantics and registration

Read-only tenant checks returned 6,546 leads and 508 property candidates on 7 September 2026. No lead returned an `Events` history. Audits therefore report missing evidence/review candidates; they cannot prove that those leads were never answered. Fifty leads had `Outcome=Won`; amounts included rental-sized values. Reports label these as closed CRM opportunities, with date/amount/attribution exceptions, rather than verified sales or commissions. Property identity in the live response uses numeric `id`, which the shared resolver supports. `CodeTable` returned HTTP 500 with the documented query flags.

Confirm and configure:

- `CRM_TIMEZONE`: the timezone of CRM timestamps that omit an offset. Do not assume the server uses the browser's timezone. Explicit-offset values work without this setting; unresolvable or ambiguous dates remain exceptions.
- `CRM_FIRST_RESPONSE_HOURS` and `CRM_INACTIVITY_HOURS`: default 24 and 168 calendar hours. Optional `CRM_BUSINESS_HOURS_JSON` defines `{timeZone,weekdays,startHour,endHour}` for a validated working-hours policy.
- Completed-contact evidence: `CRM_COMPLETED_CONTACT_EVENT_TYPE_IDS_JSON` and/or `CRM_COMPLETED_CONTACT_EVENT_TYPES_JSON`. Leave empty until their semantics are confirmed. `CRM_EVENT_HISTORY_COMPLETE` defaults false. Assignment, status and a scheduled event are not contact completion.
- `CRM_CLOSED_OUTCOMES_JSON` and `CRM_WON_OUTCOMES_JSON`: default `["Won"]`; set actual tenant meanings. `CRM_PROPERTY_ACTIVE_STATUSES_JSON` defaults to the exact observed `Active` status mapping.

Registration remains gated until all three are present: `CRM_LEAD_INSERT_VALIDATED=true`, a verified positive `CRM_LEAD_STATUS_ID`, and `CRM_LEAD_ORIGIN_IDS` mapping source names to verified positive IDs. Obtain a known-working tenant insertion example from Casafari/admins and validate it in an authorized test environment before enabling the flag. Code tables do not supply these mappings. No production insertion was attempted during implementation.

Registration checks available lead history for normalized email/phone matches, resolves the requested property/broker, preserves buying requirements and stores durable action/target claims. An uncertain response is reconciled before another write; changing the prompt or action ID cannot silently repeat the same pending contact/property insertion. Existing profile updates and combined buyer/seller intent are returned as explicit unresolved intake, not guessed CRM operations. Free-text buying requirements must be structured before saved-brief matching can claim exact matches.

`npm run crm:check` repeats read-only contract diagnostics and prints aggregate counts/shapes without contact records. It uses the configured tenant credentials.

## Idealista market research

Set `RAPIDAPI_KEY` in the root `.env` for local development, or on the gateway service in Coolify, using an active [Happy Endpoint Idealista subscription](https://rapidapi.com/happyendpoint/api/idealista17). Restart the gateway after changing its environment. The fixed host is `idealista17.p.rapidapi.com`; the browser never receives the key. No database migration or new dependency is required for this workflow.

Use the **Market research** chat starter or ask, for example: “Estimate a T2 apartment in Cascais e Estoril, Cascais, with 100 m² built area, in good condition.” A CRM reference or a Portuguese Idealista property URL also works. CRM references use the exact resolver; CRM `total_area` is not automatically considered built area. The agent asks for missing facts or offers returned locality choices when the intended area is ambiguous.

The inspected RapidAPI OpenAPI contract documents `/auto-complete` (`country`, `location_name`, `property_type`, `search_type`), `/property-search` (`location_ids`, `min_size`, `max_size`, `min_rooms`, `filters`, `page`, `result_count`, `sort_order`) and `/property-details-by-url` (`url`, `language`). The shared link's selected endpoint is autocomplete. Requests use Portugal, homes for sale, newest-first, built area ±20%, and an exact subtype filter. Bedrooms are rechecked locally: despite the provider documenting `min_rooms` as a minimum, live Portugal searches use exact T0–T3 buckets and a T4+ bucket. The envelope is `{success:true,data:...}`. The live search response uses `query` and `listings`; the published examples used `filters` and `elementList`. Both shapes are accepted, with search-context and listing validation retained. Both documented `actualPage` and live `currentPage` pagination names are accepted.

Each invocation uses at most one Idealista subject lookup, one autocomplete request and two search pages of 50 listings, with a 20-second timeout per request and no automatic retries. The tool revalidates the selected location, removes unsupported/invalid/duplicate listings, and uses up to ten comparables. It returns median €/built m² times subject area and the sample's 25th–75th percentile range, with three to five comparison links in the chat response. These are advertised asking prices, not sale transactions or a formal valuation. The sample is not exhaustive; missing condition/feature evidence is disclosed. A subject's own advertisement is excluded when its Idealista URL is known; without that identity it may remain in the sample. Fewer than three verified comparisons return links without a price estimate. Widening location or rerunning requires the user's request.

Run `node --import tsx --test test/market-research.test.ts test/turn-presentation.test.ts` for the focused mocked contract, arithmetic, intake, auth and UI-progress checks. Test facts use published and live-observed response shapes with synthetic Portuguese properties. On 9 September 2026, live autocomplete and search returned two Carcavelos Centro listings. Replaying that response through the corrected tool retained both links and returned `insufficient_data`, explicitly explaining the three-comparable minimum. All 20 focused tests and the backend build passed. The Idealista subject-detail lookup has not been verified live. `get_workflow_status` distinguishes configured credentials from an actual connectivity check.

## Verified Bonte listing URLs

Property search and matching enforce mandatory criteria and separate unknowns from exact matches. External Casafari market inventory is not in this API.

For public links, configure `CRM_LISTING_SOURCE_URL` (official sitemap `https://bontefilipidis.com/property-sitemap1.xml`) and `CRM_LISTING_ALLOWED_HOSTS=bontefilipidis.com`. Run `npm run crm:sync-links` from an administrator checkout. Each destination page must expose matching explicit reference/CRM-ID evidence; paths are not guessed. A truncated source/page scan does not replace the existing mapping. Set `CRM_LISTING_URLS_PATH` to the resulting JSON on the output volume. Default sync cap is 1,000 pages (`CRM_LISTING_SYNC_MAX_PAGES`).

## Bonte's NDA template

The default is now the supplied four-page `templates/nda/NDA_BonteFilipidis_Template2026_pt.pdf`, preserved byte-for-byte with SHA-256 `518bc1e2c62d066d985ade8f010e69960e5bafa8712b0ba6a7f9c048b5c86f01`. The gateway image includes it and `templates/nda/nda.json`; leave `BONTE_NDA_CONFIG_PATH` unset to use it. No LibreOffice conversion is involved for this PDF.

Generation adds six editable PDF fields: the complete date, receiving party's legal name and address, represented entity/person, signatory name and title. Clauses, logo, pagination and both signature lines remain as supplied. Users can edit the downloaded fields in a form-capable PDF reader and save a copy, or clarify sourced facts in chat to generate a new revision. Downloaded edits do not update the stored intake. Clause editing is not provided by these fields.

The source date prints **2025** despite the 2026 filename. The date widget covers that area with today's full Portuguese date in `Europe/Lisbon`, unless the user explicitly chooses another date. Automatic dates refresh when intake is checked or a draft is generated; explicit dates persist. This is an overlay, so underlying source text still contains 2025. The original footer's **AMI 1384** versus the body's **13824** is preserved and surfaced for review. The bundled NDA requires party identification and signatory authority evidence, with no transaction document required. Uploaded documents supply the company/legal name, address, represented entity, signer's full name and stated role/title; one document can cover all fields. Ask only for missing or conflicting evidence. The template does not add transaction-specific clauses or require invented duration/jurisdiction terms. CMI retains its property document and explicit date requirements.

Fields use 7–9 pt text and reject overflow, newlines and characters the PDF font cannot display before publishing a draft. Long legal names or addresses that cannot fit need a shorter approved value or a revised template. The PDF remains unsigned. The source checksum prevents silently applying field positions to a different PDF.

For an approved replacement, place the template and its JSON configuration on the private `workflow-config` volume mounted at `/app/config:ro`, and set `BONTE_NDA_CONFIG_PATH=/app/config/nda.json`. DOCX templates remain supported and produce editable DOCX plus LibreOffice-rendered PDF. The following illustrates custom DOCX configuration, not the bundled PDF's actual fields:

```json
{
  "version": "bonte-approved-version",
  "templatePath": "approved-nda.docx",
  "title": "Bonte NDA draft",
  "requiredDocuments": [
    { "category": "party", "label": "Party identification", "minimum": 2 },
    { "category": "transaction", "label": "Transaction details", "minimum": 1 }
  ],
  "fields": [
    { "key": "party_one_name", "label": "First party legal name", "source": "party", "required": true, "maxLength": 500 },
    { "key": "transaction_purpose", "label": "Transaction purpose", "source": "transaction", "required": true },
    { "key": "language", "label": "Language", "source": "agreement", "required": true, "allowedValues": ["English", "Portuguese"] }
  ]
}
```

An administrator must adapt fields and document counts to Bonte's approved template and representative supporting documents. Use flat placeholders such as `{party_one_name}` in the DOCX while preserving its approved clauses, tables and signature blocks. Agreement choices come from the user; party and transaction facts require document/page evidence. Missing, unreadable or conflicting evidence stops draft completion and produces a targeted request. Template loops, arbitrary replacements and invented clauses are unsupported.

The exact PDF tests use two fictional Portuguese examples, including longer names/addresses and accents, and an editable save/reopen example. They verify all four original page content streams, field values and appearances, signature preservation, evidence-backed revisions, and rejection of overflow/unsupported characters/changed templates. Run `node --import tsx --test test/document-workflows.test.ts`; optionally set `BONTE_NDA_TEST_OUTPUT_DIR=output/pdf/nda-template-tests` to retain the three review PDFs. These are test documents, not client agreements.

Visual QA rendered all three PDFs with Poppler and checked their fields. All four pages were pixel-identical to the source outside the six field rectangles (with a two-pixel antialiasing margin). Independent pypdf checks confirmed six editable canonical fields, matching widget values and non-empty appearances in each saved output. The full suite passed **192 tests**, with zero failures and one optional external-PostgreSQL test skipped; the backend build passed. This change has not been deployed.

Structured email drafts are saved and revised separately, with selected property identities and attachments retained; no email provider or sending feature was added. Mail-app shortcuts stay on the client (`mailto:`, copy, TXT download).

## Bonte's CMI template

CMI uses the exact supplied ten-page bilingual `templates/cmi/CMI__2026.pdf`, SHA-256 `4e5d59c391d26a63d526449571a5bcd6b3d8a20f0d57b08dd3424f293566661d`. The existing Docker template copy includes it; leave `BONTE_CMI_CONFIG_PATH` unset for the default, or point it to an approved configuration on the existing private config volume.

`prepare_cmi_intake` and `generate_cmi_draft` reuse the protected upload, evidence validation, expiry and revision flow. CMI and NDA intakes/drafts are separate. Clients supply readable identification and applicable spouse/corporate-authority evidence, agent identification, land registry/title, caderneta predial, use/construction licence and energy certificate. These may be combined packets; every party/property fact requires its exact source quotation and location. The intake validates evidence for the configured fields; it does not authenticate documents or independently verify signatory authority. Commercial terms require explicit user statements, and uploaded content is evidence, never instructions.

The PDF has 55 intake fields, rendered as 59 editable PDF fields across 114 widgets. Repeated identical details and PT/EN radio selections are linked. Four predefined English translations remain separate editable fields; review both languages after downloaded edits. Conditional fields handle spouse details, percentage versus fixed fees, and split payments. Invalid dates, malformed Portuguese-format amounts, inconsistent split percentages, missing/conflicting evidence and text overflow stop publication. The approved template fixes 2026, Lisbon signing, six months and other printed terms. Date widgets cover the original date placeholders with a full numeric date; the original text remains underneath the overlay.

This is a fixed-layout draft workflow: it edits completion fields, not printed clauses. The template retains alternative liens wording, slash-separated descriptions and optional clause 6, which require human review. Narrow address, marital-regime, ID, certificate and date blanks can reject otherwise valid full values at the 7 pt minimum. Never truncate identifiers or silently abbreviate legal facts. An approved shorter wording or revised source is needed when a value cannot fit. Users can revise fields in a form-capable PDF reader, or clarify facts in chat and generate another revision; downloaded edits do not update the saved intake. It remains unsigned.

Tests use two fictional DOCX evidence packets per case: an exclusive sale with a percentage fee and split payment, and a married-client lease with a fixed fee, plus a saved/reopened edit and sourced revision. Run `BONTE_CMI_TEST_OUTPUT_DIR=output/pdf/cmi-template-tests node --import tsx --test test/document-workflows.test.ts` to retain three sample PDFs. Tests also cover missing evidence, conflicts, obsolete fees, invalid dates/payment totals, overflow, unsupported characters, template checksum, conversation/actor separation and retention. Real client documents, scans/OCR and a live model conversation were not tested.

Visual QA rendered all three outputs, corrected cover/date placement, and confirmed all 30 pages were pixel-identical to the source outside field rectangles with a 3-pixel antialiasing margin. Independent pypdf checks verified the canonical field tree, widget values/appearances and editability. The full repository suite passed 194 tests (one optional external PostgreSQL test skipped); backend and web builds passed. No deployment was performed.

## Team Google Calendar

Configure a Google OAuth client and authorize the intended team account with `https://www.googleapis.com/auth/calendar.events` and `https://www.googleapis.com/auth/calendar.readonly` (or the broader calendar scope if already approved). Grant that account access to the selected team calendars. Store `GOOGLE_CALENDAR_CLIENT_ID`, `GOOGLE_CALENDAR_CLIENT_SECRET` and an offline `GOOGLE_CALENDAR_REFRESH_TOKEN` in deployment secrets.

Set `GOOGLE_CALENDAR_ALLOWED_IDS` to canonical calendar IDs (`primary` is rejected because aliases could bypass shared-calendar locking), `GOOGLE_CALENDAR_WORKSPACE_IDS` to the allowed Bonte workspace IDs and `GOOGLE_CALENDAR_AUTHORIZED_ACTOR_IDS` to authorized actor IDs (comma-separated). Obtain IDs using `calendar_workflow_status` from each intended user's signed-in chat; they are Bonte scope IDs, not emails or raw authentication IDs. The legacy singular `GOOGLE_CALENDAR_WORKSPACE_ID` is also supported. The development assistant's Google connection does not authorize the deployed application.

The agent can save proposals before Google is connected. Booking checks accessible calendars, explicit timezone/DST, consecutive-viewing order and travel buffers. Only a confirmed provider event is called booked. Attendee responses remain separate; invitations are sent only when requested. Retries, reschedules and cancellations retain the same event ID and reconcile uncertain writes. Availability checks and event creation are separate Google operations, so another calendar client can still book between them. Bonte serializes its own writes to a shared calendar; it cannot lock Google Calendar globally.

Access is bounded to 100 configured workspaces and 10,000 saved viewing records per workspace; hitting the record cap blocks booking until coverage is resolved. Provider behavior was exercised with controlled HTTP responses. A real authorized booking/reschedule/cancel smoke check remains necessary after account setup. No live events or invitations were sent during development.

## Buyer matching across CRM and Idealista

Open a lead's detail drawer and select **Match properties**, or use **Match a buyer** in the chat starters. Both use `match_saved_buyer`. An exact lead ID resolves its saved buyer brief; missing or ambiguous briefs return intake before any property search. Save explicit mandatory/preferred requirements with `save_buyer_brief`, including the lead ID. A budget ceiling and locations are required. Buyer searches default to sale/EUR; explicit alternatives are preserved, with unsupported Idealista scope reported separately.

Results show CRM/Idealista source links, matched and unknown requirements, retrieval dates and coverage. Each search scans up to 100 pages per source (10,000 CRM / 5,000 Idealista records at most); `maxPages` can lower the bound. Provider limits, invalid/repeated pages and failures remain visible. CRM and Idealista use separate location hierarchies. Mandatory cities resolve to a verified Idealista concelho, including when an older brief mistakenly saved the same-named district. Descendant location IDs establish city membership even when the `municipality` label names a parish. Supported property types and all applicable bedroom buckets are requested upstream, then mandatory limits are checked locally. CRM currency symbols/codes and explicit Portugal country names are normalized before matching. Searches exceeding the provider’s verified 50-page paging limit split into inclusive price ranges within the same request budget, deduplicating shared boundaries. Pagination counts unique source IDs independently of validation: development-only pages no longer stop the search, and omitted development/invalid adverts are reported separately. Missing features and incompatible area bases remain unknown; a generic house does not prove a villa subtype, and a parking space does not prove an enclosed garage.

Use **Next/Previous** to browse saved results in pages of 20. Selection carries across pages through `get_buyer_matches`, without new provider requests. **Edit requirements** opens brief editing; **Refresh matches** starts a new search. Select up to 20 properties and choose **Prepare shortlist**: the workflow refreshes selected details, reports price changes, omits unavailable/unverifiable listings and saves a lead-linked HTML presentation plus an unsent email draft. Unknown mandatory criteria are labeled in the presentation. Attachments use existing S3 storage and retention. No recurring search or sending is enabled.

The existing `workflow_records` table stores `buyer_match` and `buyer_shortlist` records. No new dependency or database migration is required. Restart the gateway to load the tools and rebuild/restart the web service for production. Keep `RAPIDAPI_KEY` and the existing Happy Endpoint subscription on the gateway. The provider's Portugal search envelope and detail fields (`moreCharacteristics.lift`, `swimmingPool`, built/usable area, and direct `priceInfo`) were checked live on 9 September 2026. Runnable checks: `node --import tsx --test test/buyer-matching.test.ts test/web-gateway.test.ts` (the gateway tests require local test MinIO).
